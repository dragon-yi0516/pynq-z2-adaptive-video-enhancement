日志里的三条直接证据（`stage08_auto_schedule/sched.log`）：

```
[06:32:23] IP 版本 0x0001020D (阶段 13)
[06:32:24] 门限拒绝：MLP 说 2，但特征 (65, 37, 27) 离它那一类太远/不是最近类 -> 保持模式 1
[06:32:58] 心跳 t=35.1s MLP=1 模式=1：MODE_SEL=1 MLP_OUTPUT=2 ... 特征=(68, 38, 28) PARAM=212

```

第三行是最能说明门限作用的一条：**模型中途改口说 2，但门限判该帧不可信
（(68,38,28) 的最远/最近距离比超过 1.5 倍余量），于是模式保持 1 不动** ——
没有它，画面会在场景过渡时来回抖。

> 答辩时如果被问"为什么要拒这么多次"：这 1461 次是我**手动扫灯**、画面从一个类别
> 过渡到另一个类别的过程中产生的中间地带帧，模型对它们的判决本来就不该信；
> 门限的职责就是"宁可不动，也不乱切"，所以 60 秒里只真正切了 8 次。
>
> 历史对照（可当趋势看）：阶段 12 上跑过 15 次切换 / 拒绝 999 次 / min_hold 挡下 382 次；
> 10-08 慢速演示那次 min_hold 只挡下 38 次。切换次数随"扫场景的快慢"变化很大，不是固定值。

门限规则（答辩可讲）：特征必须**归一化距离 ≤ 12σ** 且**判决类必须是最近类**，
否则保持当前模式 —— 实测把 `(34,8,40)` 被判 0、`(51,24,29)` 被判 0/2 这两类
外推乱判都挡掉了，而正常帧（0.2σ~10.5σ）一个不误杀。

## 10. 固定 vs 连续自适应（方案书步骤 5）

**2026-10-15 实测（`tools/step5_compare.ipynb` 三格分档跑，锁定 736 行 / 增益 0x20，成对测量）**

| 场景 | 实测 f | 目标中心 | 摆位 | mode0 固定 ×1.5 | mode0 自适应 | 收益 |
|------|--------|---------|------|----------------|-------------|------|
| 暗光 | (7, 0, 10) | (9.7, 0.2, 17.2) | 距 7.7 ✓ | 均值 12.7，饱和 0.0% | **PARAM=255(×1.99)**，均值 16.4，饱和 **0.0%** | 提亮 **+29%** 且不过曝 |
| 逆光 | (59, 41, 26) | (66.4, 44.6, 21.4) | 距 9.4 ✓ | 均值 82.7，饱和 22.5% | PARAM=183(×1.43)，均值 81.2，饱和 22.3% | 见下方说明（增益压不住已有高光） |
| **常规** | (101, 62, 36) | (96.5, 68.6, 29.9) | 距 10.0 ✓ | 均值 163.4，**饱和 29.4%** | **PARAM=128(×1.00)**，均值 117.4，饱和 **0.4%** | **饱和率 29.4% → 0.4%，降 29.0 个百分点** |

`MLP_OUTPUT` 三档全部判对（0 / 1 / 2），摆位全部命中，脚本自检打印
「三档齐、摆位全 OK → 这张表可以直接进报告」。

系统**实际会选用的模式**（暗光→mode 0、逆光→mode 1、常规→mode 2）下，饱和率分别是
**0.0% / 0.0% / 0.6%**，两种强度都在 1 个点以内 —— 也就是说正常工况本来就不会过曝，
那 29.4% 只出现在"把 mode 0 增益硬套到常规亮度画面"这个阶段 7 的老行为上。

**报告里建议这么写**：

> 固定强度沿用阶段 7 的行为（mode 由场景决定、强度写死 `PARAM=192` = ×1.5）。
> 在同一场景、同一次运行下成对测量：常规档（摆位命中，f=(101,62,36)）出现 **29.4% 的像素饱和**；
> 连续自适应按实测亮度反推增益，算回 `PARAM=128`（×1.0），**饱和率降到 0.4%**（降 29 个百分点）。
> 暗光档则是另一半故事：自适应把增益提到 ×1.99（均值 +29%），**饱和率仍是 0.0%** ——
> 该提亮的提亮、该收的收。

**答辩可能被追问的一点（先想好）**：逆光档的 mode 0 两行都在 22% 左右，看着"自适应没起作用"。
原因是这一档画面里**光板本身就打到接近 255**（实测 std = 96），增益从 ×1.5 降到 ×1.43
也只能压低"整体亮度"，压不住"场景里已有的高光"。三点回应：

1. 逆光档系统实际走的是 **mode 1**（对比度补偿），那一行是 **0.0% → 0.0%**，本来就不会过曝；
2. mode 0 是"增益"路，它的职责是把暗画面提亮，不是压高光 —— 拿它去处理带大面积极亮区的画面，
   属于把方案 A 的器件用在了方案 B 的场景上；
3. 真要连高光一起管住，得把**高光占比**也纳入增益决策（现在 `gain_param()` 只看平均亮度 f1）
   —— 这条可以写成"后续改进方向"，比硬说"没问题"更稳。

**推荐直接打开 `tools/step5_compare.ipynb`** —— 它是**一格一档**的结构（暗光 / 逆光 / 常规各一格，
摆好一档测一档），最后还有一格把三档合并成表。要独占 PL，别和别的 overlay 格同时跑。

想一口气跑完（连续三个倒计时）也可以，在任意一格里：


分档跑就是给每格加 `--only`：`s5.main(["--only", "0", "--wait", "10", "--shots", "3"])`
（0/1/2 = 暗光/逆光/常规）。CSV 是**合并**写的：三格跑完是一张三行的完整表，
单独重测某一档也只换掉那一行；想看合并结果随时 `s5.report()`。
