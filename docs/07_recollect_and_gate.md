# 补采数据 → 体检 → 重训（优化方案「步骤 4」的操作手册）

这份文档是 `docs/05_optimization_plan.md` 里**步骤 4**（"补采训练数据 + 重训"，
备注是"收益最大"）的可执行版本，同时把这份工程实测踩到的两个坑变成**自动判据**。

它不动现有的验证成果：阶段 7/12/13 的 bitstream、`lib/exposure.py`、
`tools/box_calibration.ipynb` 都保持原样。

---

## 1. 为什么必须重采

当前 `data/features.csv` 是 600 行，但每类的**不同取值个数**是：

| label | 帧数 | f_luma 不同取值 | f_luma2 | f_grad |
|-------|------|----------------|---------|--------|
| 0 暗光 | 200 | **2** | **1** | **3** |
| 1 逆光 | 200 | 9 | 7 | 5 |
| 2 常规 | 200 | 18 | 16 | 17 |

也就是"三个静止画面各拍 200 帧"。后果实测过：

* 特征落在中间地带（`f_luma = 30`）时被判成类别 1，而它离类别 0 的中心（10）
  比离类别 1（67）更近 —— 模型只见过三个点，中间是"任意输出"。
* 答辩时问一句"每类采了多少个不同场景"就会露。

好消息：三个**中心**（10 / 67 / 109）本来就等于盒子标定的三个档位，
所以补采之后模型结构、HLS、bitstream 流程都不用变，只是权重更可靠。

## 2. 三步走

### 第一步：采（盒子 + 手动曝光 + 每类换 3~5 种摆法）

```bash
cd ~/OV5640_capture_only/ai_video
python3 tools/collect_dataset.py                       # 默认：盒子模式，每类 3 轮 x 60 帧
python3 tools/collect_dataset.py --rounds 4 --per-class 60
python3 tools/collect_dataset.py --auto-exposure       # 不用箱子时保留自动曝光
```

**默认会切手动曝光**（`lib/exposure.py` 的 `set_manual`）。这一步不能省：
箱子里把灯调暗时，自动曝光会把画面亮度顶回去，暗光档根本采不出来
（实测遮镜头 `f_luma` 最低只到 27，而目标中心是 10）。

脚本会在采集前提示每一轮怎么摆，采完自动跑体检、并画一张分布图
（`data/features_dist.png`）。**图的判据**：每一簇要是一团云，不是一个点。

### 第二步：体检（闸门）

```bash
python3 tools/check_features.py                 # 采完自动跑，也可手动跑
python3 tools/check_features.py --no-fail       # 只体检，不改退出码
```

| 判据 | 要求 | 挂了说明什么 |
|------|------|-------------|
| C1 | 每类样本数够（≥30，方案书 200） | 采集被打断 |
| **C2** | **每类"不同特征三元组"≥20（低于 5 判死）** | 那一类还是一个静止的点，模型没见过它的范围 |
| C3 | 不能有整列恒定的特征 | 移位取太粗 / 硬件没统计到 |
| **C4** | **三类中心两两分得开（中心距 >= 2x 散布半径）** | 两类糊在一起，重训也救不回来 |
| C4b | 类中心跟原标定中心（10 / 67 / 109）差多远 | 差得多 = 现有模型/bit 不能直接复用，要重训（只提醒） |
| **C5** | **类间"没样本的中间地带" < 4 倍类内 std（>8 倍判死）** | 实机落在中间地带判决任意 |
| C6 | 暗光类亮度 < 20（>30 判死） | 手动曝光没生效 / 箱体漏光 |
| C7 | 暗光类还留着细节（f_grad ≥ 常规类的 40%） | 暗光档变成了"全黑"，换张有纹理的卡 |
| C8 | 类内覆盖宽度（f_luma ≥ 10 / f_luma2 ≥ 6 / f_grad ≥ 5） | 某一维被模型当"身份证"，板上一漂判决就跳 |

**有 FAIL 就重采那一类，别急着重训。**

### 第三步：重训（自动躲开量化饱和）

```bash
# 板子上
03_mlp_train.ipynb          # 已改用 mc.train_for_quantization(...)
04_mlp_quant_export.ipynb   # 导出 weights/mlp_weights.h

# PC 上先空跑一遍（不接板子）
python3 tools/offline_check.py
```

`train_for_quantization()` 会自动挑一组"准确率够、量化又不饱和"的超参，
并把余量打印出来（`max|w1_folded|` 离 0.5 还有几倍）。

为什么需要它：训练时归一化会被折进第一层（`w1_folded = w1 / std`），
而定点约定要求 `|w1_folded| ≤ 0.5`（Q8.8 里它还要再乘 65536 才塞进 int16）。
类内变化少的时候折进去的权重容易超标，`quantize()` 会直接报
「w1 量化后饱和」—— 这个坑以前要靠人肉调学习率。

**权重变了必须重出 bit**：`make_tv.py` → HLS → `bash build_overlay.sh 12`，
否则板上跑的还是旧权重。

## 3. 顺手回答"这是不是就是个亮度分类器"

`docs/04_demo_box.md` 第 8 节提出了这个问题，`check_features.py` 会给出数据侧的答案：

```
只用 f_luma 做两级阈值分类的准确率 = ?%
corr(f_luma, f_luma2) = ?
去掉亮度趋势后，逆光 vs 常规 的对比度差异 d = ?
```

* 亮度准确率 100%、d 很大 → 亮度是主判据，但对比度**带着独立信息**，
  现场按 doc 04 第 8 节做那个实验（把灯固定到 `f_luma ≈ 77` 换不同对比度的卡片），
  看 MLP 会不会在 1/2 之间翻转，把结果写进报告；
* d 很小 → 老老实实说"主判据是亮度，对比度辅助区分逆光"，别硬撑。

## 5. 实战案例：10-11 那次为什么采废了（留档，别再犯）

板子上跑 `02_feature_collect.ipynb` 得到的结果：

```
第 0 步 扫曝光   256 行→luma 4.28  384→4.26  512→4.33  640→4.38  736→4.36
检查 A          luma 4.35  contrast 0.64  sharp 0.39  f=(3,0,5)
三类采集        label0 luma 3.0 / label1 10.4±15.0 / label2 3.5     目标 10 / 67 / 109
```

**判读**：`contrast 0.6 / sharp 0.4` 是纯传感器噪声底；曝光从 256 扫到 736，
luma 一直 4.3 完全不动 —— 这两条合起来说明**采集时几乎没有光进镜头**
（箱盖合着 / 灯没开 / 灯没供电 / 镜头孔被密封材料挡死），
所以扫描那一步也是在黑箱里做的，扫出来的东西没有意义。
label1 的 `10.4±15` 是中途有光进来过一下。

**排查顺序（从便宜到贵）**：

1. `02_feature_collect.ipynb` 第 0 格「光线自检」：自动/手动各读一次 luma。
   两个都 ≈4 → 光没进来（硬件问题）；有差别 → 光正常，是标定/摆法问题。
2. 光没进来时依次查：灯的电源和调光旋钮 → 箱盖 → 镜头孔（别把镜头也贴死了）。
3. 光能进来但到不了 luma 124：用新的「曝光 × 增益」扫描格。
   注意曝光上限约 736 行，光靠加曝光可能不够 —— **增益也要往上扫**
   （上一版固定在最小的 0x10，是个盲点）。

**这次已经加上的三道保护**：

* 第 0 格光线自检（自动 vs 手动），2 分钟分辨"没光"和"寄存器没生效"；
* 第 1 格扫描同时扫曝光 × 增益，并在最亮读数 < 20 时明确提示"画面上根本没有光"；
* 采集循环里**每轮先检查当前 `f_luma` 是否在该类的目标带内，不在就跳过不采**，
  并在末尾列出被跳过的轮次；
* 体检的 C4 升级成"中心偏离 60% 以上直接判 FAIL"，并会点出"整份数据都贴在噪声底"。

## 6. 重训之后**必须**重出 bit（现在有工具盯着）

2026-10-11 踩过：训练完导出了新权重，但忘了重出 bitstream，
于是板上跑的**还是旧模型**，monitor 看到的所有判决都是旧权重给的 —— 白折腾一轮。

```bash
python3 tools/check_weight_sync.py        # 退出码 1 就是还没同步好
```

它查三件事：

1. `weights/mlp_weights.h` 和 `stage05_mlp_hls/src/mlp_weights.h` 是否一致（sha256 指纹）；
2. 权重里的维数 / 移位是否和工程约定对得上；
3. **bitstream 有没有比权重旧** —— 旧了就说明板上跑的一定还是旧模型。

实测输出（10-11 那次就是这个问题）：

```
权重 : weights/mlp_weights.h   指纹 67f2b404e507ed82   修改时间 10-11 10:18
HLS  : stage05_mlp_hls/src/mlp_weights.h   一致
BIT  : overlay/cv_ov5640.bit   修改时间 10-05 21:27
       -> **bitstream 比权重旧 7972 分钟**
[结论] 有 1 个问题：跑 `bash build_overlay.sh 12` 重出 bit 之后再看 monitor
```

### 配套：`lib/adaptive.py` 现在跟着数据走

以前三类中心（以及置信度门限 25、三处参数锚点）是**写死的第一版数据**。
重训之后中心会动（实测 暗光 9.8→16.8、逆光 67.4→63.7、常规 109.3→89.4），
写死的中心会让门限指着错的地方 —— 后果很隐蔽：

```
常规档特征 (89,38,38) 离旧中心 (109.3,54.7,34.6) 有 26.3 > 门限 25
-> 每次都被判成"不可信" -> mode 2 永远切不进去
```

现在这些都从 `data/features.csv` 现场算：

* 三类中心 / 散布：`load_class_stats()`；
* 置信度门限：**逐类** = `max(2.5 × 该类散布半径, 0.5 × 到最近类中心的距离)`
  （暗光类散布大、离得远 -> 门限宽 ~27；逆光/常规只隔 29 -> 门限紧 ~15）；
* 三个参数映射的锚点：增益的 target/floor、逆光补偿的对比度区间、锐化的细节区间。

改了 `features.csv` 而进程还活着时，调一次 `adaptive.reload_from_csv()` 即可刷新。
