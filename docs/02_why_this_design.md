# 为什么这么设计（逐条对照方案书）

## 1. 插入位置：demosaic 之后、VDMA0 之前

方案书的意图是“让视频流经过一个自定义 AXI4-Stream IP”。
我们把这个 IP 放在 `v_demosaic_0/m_axis_video -> axi_vdma_0/S_AXIS_S2MM` 之间。

原因：

* 这里已经是 24bit RGB + `tuser`/`tlast` 的标准视频 AXIS，接口完全匹配。
* 处理结果会同时进入 **Jupyter 抓帧**和 **HDMI 显示**，
  阶段 7 的“画面效果明显不同”既能被眼睛看到，也能被抓图存档。
* `v_demosaic` 内部有帧缓存，画布节奏稳定；插一个纯流水线 IP 只增加几拍延迟，
  不会破坏已经调通的采集通路。
* 只要这一步，阶段 6/7 的 MLP 与可重构阵列都能直接复用同一条流，
  不需要二次改 BD。

## 2. 一个 IP 逐阶段长大，而不是每阶段新建一个 IP

方案书的阶段 1/2/3/6/7 都在同一段视频流上做文章。
如果每个阶段新建一个 IP，Vivado 里会留下一串互相冲突的 AXI 地址段，
Jupyter 侧也要反复改名字。

因此我们只维护**一个** IP `axis_video_proc`：

* 阶段 1：只有 AXIS 直通。
* 阶段 2：加 AXI-Lite（VERSION/MODE_SEL/FRAME_CNT/VBLANK_CNT）。
* 阶段 3：加特征提取累加器。
* 阶段 6：加 MLP 推理实例。
* 阶段 7：加三模式可重构处理。

每个阶段的 HDL 文件都放在各自子目录里，**版本号体现在 `VERSION` 寄存器**，
这样“现在板子上跑的是哪一版”一目了然。

## 3. 硬件只做累加，除法交给 Python

`sumY / sumY2 / sumGrad` 在硬件里只是加法器，非常省资源；
除法、开方、归一化交给 Jupyter。理由：

* FPGA 上做除法/开方要耗 DSP 和若干时钟周期，而且帧率要求并不需要这么急。
* 公式要调（比如换成用中位数、换梯度算子）时只改 Python，不用重新综合。
* 只要保证**训练和推理用同一套公式**，分类精度不受影响。

## 4. 定点 Q8.8 而不是浮点

MLP 权重用 Q8.8（1 位符号 + 7 位整数 + 8 位小数，存成 `int16`）。

* 输入特征量级在 0~255 附近，8 位小数足够。
* 乘加用 `int32` 累加不会溢出（3×8 个 `int16×int16` 乘积之和远小于 2^31）。
* 移位 `>>8` 还原小数位，正好是 Verilog 里最便宜的 `>>>`。
* `data/` 里保存了量化前后的对比脚本，任何一次改动都能立刻回归。

## 5. 用 tuser 做“无撕裂切换”

视频流里没有独立 vsync，我们就把 `tuser` 当作帧边界，
在 IP 内部用它重采样 `MODE_SEL`。这样 CPU 在任何时刻写寄存器都不会撕裂画面，
软件侧只需要轮询 `VBLANK_CNT` 来知道“换模式已经生效”。

## 6. 为什么 notebook 分阶段而不是一个巨型 notebook

* 每个阶段的验证目标不同（阶段 0 看 IP 列表、阶段 2 看寄存器、阶段 3 看 CSV…），
  分开后任何一步出问题都能定位到具体阶段。
* 答辩演示时只跑需要的几个 notebook，节省板子资源。
* 每个阶段目录里的 `VERIFY.md` 就是验收清单，照着打勾即可。

## 7. 与方案书明确不一致的地方（都是有意为之）

| 方案书写法 | 本工程写法 | 原因 |
|-----------|-----------|------|
| 无 DDR 的纯直通链 | demosaic→IP→VDMA0→VDMA1→HDMI | 复用已调通的采集，风险最低 |
| `CONTRAST` 直接是一个寄存器 | `LUMA_SQ_SUM` + `PIXEL_CNT` 由软件算方差 | `sumY2` 需要 48bit，单个 32bit 寄存器放不下 |
| IP 名 `axis_video_passthrough` | IP 名 `axis_video_proc` | 它后面还要长成完整处理链，名字保留“passthrough”会误导 |
| notebook 里长时间 `while True` | 调度循环单独做成 `auto_schedule.py` | Jupyter 长循环容易卡内核，用 `!python` 或后台跑更稳 |
