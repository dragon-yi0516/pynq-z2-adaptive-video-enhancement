# 「处理前 / 处理后」对比显示的三个方案

答辩想同时展示"原图"和"处理后的图"，有三种做法，代价差很多。

## 现状：HDMI 上只有一路画面

```text
OV5640 → v_vid_in_axi4s → v_demosaic → axis_video_proc → VDMA0 → DDR
                                              ↑
                        原始像素流在这里就没有分叉
        DDR → VDMA1 → v_axi4s_vid_out → rgb2dvi → HDMI
```

`axis_video_proc` 插在 demosaic 和 VDMA 之间，**原始流没有被缓存**，
所以 HDMI 上拿不到"未处理"的画面 —— 要分屏就必须让它分叉。

## 方案 A：Jupyter 并排 + 差值（推荐先做，零硬件改动）

现成 notebook：`stage11_demo/10_split_compare.ipynb`

**关键技巧**：`MODE_SEL=0` + `PARAM=128` 就是 **×1.0 完全直通**
（增益公式 `v = (c * PARAM) >> 7`，PARAM=128 时 `v = c`）。
所以不用改硬件，切一下这两个寄存器就能抓到"原始画面"，
抓完再切回自适应模式抓处理后的图，然后并排 + 差值热力图显示。

| 优点 | 缺点 |
|------|------|
| 零风险、当天可用 | 不是在 HDMI 上实时分屏，而是投影笔记本 |
| 能做**差值热力图**，比单纯并排更有说服力 | 两帧之间画面不能动 |
| 顺便产出量化对比表（亮度/std/水平差分/饱和率） | |

## 方案 B：HDMI 真分屏（只显示画面的左半边，1:1 不缩放）

**原理**：输入是 1280 宽的一路流，输出也要 1280 宽。把"每一行"这样安排：

```text
屏幕左半 640 宽  ←  原始画面的第 0~639 列
屏幕右半 640 宽  ←  处理后的第 0~639 列（同一区域！）
```

两边内容**完全一致**（都是画面左半边），只有"处理/未处理"的区别 → 对比最直观。
而且 640×720 放进 640×720 的格子，**1:1 不缩放**，不需要 scaler。

### 要改什么

1. **HDL**（建议新建 `stage13_split/`，不要动已验证的 stage12）：
   - 加一个 **640×3 字节的行缓冲**（约 1920 字节 BRAM），存"处理后的第 0~639 列"
   - 列计数**已经有了**（`q_col`，四象限统计用的那个）
   - 输出级加一个选择：`col < 640` 时输出**原始像素**（同时把处理后的写进行缓冲）；
     `col >= 640` 时输出**行缓冲里的处理后像素**
   - `tvalid/tuser/tlast` 不用改（还是每行 1280 个像素、行末 tlast）
2. **BD**：不用改（IP 的接口和端口都没变）
3. **软件**：不用改（notebook、调度脚本都照旧）
4. **必须重跑** `bash build_overlay.sh 13` 并过时序

### 代价与风险

| 项 | 说明 |
|----|------|
| 视野 | 只剩画面的左半边（右半边被丢弃） |
| 资源 | +1920 字节 BRAM（很小） |
| 时序 | 中等风险：多了一条"行缓冲读 → 输出寄存"的路径 |
| 工期 | 约半天（改 HDL + 重跑 + 验证），含一次 30~40 分钟的综合 |

## 方案 C：HDMI 全视野分屏（左右各占半屏显示完整画面）

要显示**完整**的两路画面，每路只能占 640 宽，而原始是 1280 宽
→ 需要 **scaler**（水平 2:1 缩小）。

本设计里没有 scaler，而 Xilinx 的 Video Scaler IP 在 2024.2 里也不好找
（视频 IP 系列大多已弃用）。

**不建议赛前做**：需要新 IP、新 BD、新的时序收敛，风险和工作量都不成比例。

## 建议

1. **先做方案 A**（已经给你 notebook 了）—— 零风险，答辩投影效果已经够用，
   而且差值热力图能直接说明"处理改变了哪些像素"。
2. 如果时间和精力允许，再考虑**方案 B** —— 它是真正在 HDMI 上分屏，
   而且左右内容一致、对比最直观，代价是半天工期 + 一次重跑。
3. 方案 C 放弃。
