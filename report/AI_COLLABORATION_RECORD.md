## 2. 设计阶段 LLM 辅助（对应报告 4.1）

### 2.1 架构设计咨询

**优化目标**

在“重建一条无 DDR 直通链”和“复用已调通的 VDMA 链路”之间做选择，
同时保证处理结果能进 Jupyter 抓帧和 HDMI。

**用户输入（提示词）**

```text
我现在有一个已经跑通的 PYNQ-Z2 + OV5640 采集工程：
OV5640 -> v_vid_in_axi4s -> v_demosaic -> VDMA0 -> DDR -> VDMA1 -> HDMI。
我想在视频流里插一个自定义 AXI4-Stream 处理 IP，做逐像素统计和图像增强。
请比较两种方案：
1) 重建一条不带 DDR 的纯直通链；
2) 把 IP 插在 demosaic 和 VDMA0 之间。
从风险、调试成本、Jupyter/HDMI 双输出、后续扩展四个角度分析。
```

**LLM 回答（摘要）**

建议方案 2：插在 `v_demosaic_0/m_axis_video` 和
`axi_vdma_0/S_AXIS_S2MM` 之间。理由：

* 这里是整条链路唯一的 24-bit RGB + `tuser/tlast` 原始像素流；
* 处理结果同时进 Jupyter 和 HDMI；
* `v_demosaic` 自带帧缓存，插纯流水线 IP 不破坏采集；
* 重建直通链等于推翻已验证的 VDMA 通路，风险和收益不成比例。

**采用建议**

采用方案 2；把 IP 命名为 `axis_video_proc`，而不是
`axis_video_passthrough`，因为后续还要长成完整处理链。

**验证**

`overlay` 的 IP 清单里同时出现 `v_demosaic_0`、`axis_video_proc_0`、
`axi_vdma_0/1`；板上 HDMI 出图，Jupyter 能抓帧。

### 2.2 软硬件划分

**优化目标**

决定哪些放 PL、哪些放 PS，避免“什么都塞进 PL”或“PS 逐像素太慢”。

**用户输入（提示词）**

```text
视频是 1280x720@30，每帧 921600 像素。
我要统计亮度、亮度平方、梯度和四象限亮度，再做一个 3 分类 MLP。
请给出 PL/PS 划分建议，并说明理由：
哪些必须放 PL，哪些放 PS 更方便调参？
```

**LLM 回答（摘要）**

* 逐像素统计放 PL：PS 逐像素循环太慢，且会占满 CPU；
* MLP 放 PL/HLS：每帧一次，70 ns，确定性强；
* 置信度门限、四象限规则、防抖、PARAM 计算放 PS：
  规则需要反复调，改 Python 不用重综合；
* 四象限统计放 PL：4 个累加器，成本极低，但能把“空间布局”带进决策。

**采用建议**

形成“统计用硬件、决策用软件”的划分；四象限规则放 PS，
改阈值只需要改 `lib/adaptive.py`，不需要重出 bitstream。

**验证**

资源报告 LUT 29.82% / FF 19.49% / BRAM 22.50% / DSP 26.36%；
改 `u_lo/u_hi` 后只重启 Python 进程，硬件不变。

### 2.3 状态机/帧边界切换

**优化目标**

视频流没有独立 vsync，CPU 任意时刻写 `MODE_SEL` 不能造成半帧换模式/撕裂。

**用户输入（提示词）**

```text
我的 IP 挂在纯 AXIS 像素流上，只有 tuser（帧首）和 tlast（行尾），
没有 vsync/vblank。CPU 写 MODE_SEL 时，怎么保证切换只发生在帧边界？
```

**LLM 回答（摘要）**

在 IP 内部用 `tuser` 上升沿把 `MODE_SEL` 重采样成 `mode_active`；
CPU 随时可写，但真正生效在下一帧第一个像素。
`PARAM` 用同样的 `param_active` 同步锁存。

**采用建议**

采用 `mode_active <= reg_mode_sel` 在 `sof_beat` 上更新；
软件侧用 `VBLANK_CNT` 轮询“切换已生效”。

**验证**

`06_mode_manual.ipynb` 切换三档不撕裂；
`auto_schedule.py` 的日志显示切换落在帧边界。

### 2.4 时序设计

**优化目标**

阶段 3 在 100 MHz 下 WNS=-5.423 ns，路径从 `v_demosaic_0` 输出 mux
到 `acc_luma2_reg[45:37]`。

**用户输入（提示词）**

```text
阶段 3 时序不收敛：WNS=-5.423 ns，TNS=-289 ns。
最差路径从 v_demosaic 输出 mux 到本模块 48 位累加器。
当前一个周期里做了：三个乘法求亮度 -> 平方 -> 48 位累加。
请给出拆分方案，并说明每级应该放什么。
```

**LLM 回答（摘要）**

第一版建议切一刀：亮度/梯度一级、平方一级。
实测 WNS 改善到 -3.92 ns，但仍不收敛；最差路径变成
`v_demosaic -> grad16_a`，说明源头长走线还在关键路径上。

第二次建议：

* 统计源改成模块自己的寄存器 `px1_*`，把 `v_demosaic` 输出 mux 摘出去；
* 分成四级：亮度 → 梯度 → 平方 → 累加；
* 帧边界锁存跟着流水延迟，用 `sof_s3`。

**采用建议**

采用四级流水；stage7 报告 WNS=+0.134 ns，失败端点 0。

**验证**

`stage07_reconfig_array/timing_v3.rpt`：
`All user specified timing constraints are met.`。

## 3. 实现阶段 LLM 辅助（对应报告 4.2）

### 3.1 自定义 IP 与 AXI-Lite

**优化目标**

把统计、四象限、MLP 握手、像素处理放进一个 IP，寄存器地址固定。

**用户输入（提示词）**

```text
我要把统计、四象限、MLP 握手和三种像素处理放进一个 AXI-Lite IP。
请给出寄存器表建议：哪些放只读、哪些读写、地址怎么排，
以及 Python 侧怎么封装，避免 HDL/Python/文档三处写岔。
```

**LLM 回答（摘要）**

* 0x00 MLP_OUTPUT、0x04 MODE_SEL、0x08 STATUS、0x0C VERSION；
* 0x10~0x28 统计原始值；
* 0x34 PARAM、0x38/0x3C 四象限；
* 以 `docs/01_register_map.md` 为唯一权威，Python 常量与 HDL case 同步；
* 增加 `VERSION=0x0001_RRSS`，板上读回就能确认阶段/修订。

**采用建议**

采用该映射；新增 `skill/axil_register_contract` 做地址一致性检查。

**验证**

`lib/test_regs.py` 通过；板上读 `VERSION` 能区分 stage12/13。

### 3.2 HLS MLP 与 Q8.8 量化

**优化目标**

把 3-8-3 MLP 做成 HLS IP，和 Python 定点参考逐位一致。

**用户输入（提示词）**

```text
我训练了一个 3-8-3 MLP，输入是三个整数特征，输出三类。
想在 Vitis HLS 里做 Q8.8 定点推理，和 Python 的 predict_fixed_raw 逐位一致。
接口用 3 个标量 + 返回值，还是指针输出？握手用 ap_ctrl_hs 怎么接？
```

**LLM 回答（摘要）**

* 用 3 个标量 + 返回值，端口最少，BD 接线简单；
* 全部用 `ap_int`，右移用算术右移；
* 权重 Q8.8，第一层归一化折进 `w1/b1`；
* 用 `train_for_quantization()` 自动避开 `w1` 饱和；
* HLS 侧 `#pragma HLS PIPELINE II=1`，全展开。

**采用建议**

采用返回值接口；`ap_start` 拉高并保持，直到 `ap_done`，避免
`ap_ready` 版本差异导致握手卡死。

**验证**

`TV_N=124 fail=0`，`CSIM PASSED`；HLS 报告 II=1、Depth=7、
Estimated Fmax 137.08 MHz。

### 3.3 连续 PARAM

**优化目标**

阶段 7 的三档写死强度在正常亮度下会把 26.7% 像素打到 255；
希望强度随场景连续变化。

**用户输入（提示词）**

```text
现在三种模式是写死强度：mode0 ×1.5、mode1 分段、mode2 |Δ|/2。
正常亮度下 mode0 有 26.7% 像素饱和。
请设计一个连续 PARAM：越暗增益越大、到目标亮度回 1.0；
逆光按对比度给补偿；锐化按细节量给强度。
```

**LLM 回答（摘要）**

* mode0：`PARAM=128` 是 ×1.0，`255` 是 ×1.99；
  按实测亮度在 `floor=暗光中心`、`target=常规中心` 之间线性插值；
* mode1：对比度越高，补偿越强；
* mode2：细节越少，锐化越强，细节多时收敛以免放大噪声；
* 参数在帧边界与 `MODE_SEL` 同步锁存。

**采用建议**

采用；后续用实测发现 `stretch_param` 方向写反，按板上 `std` 方向翻转。

**验证**

常规场景饱和率 29.4% → 0.4%；暗光均值 +29% 且饱和 0.0%。

### 3.4 四象限空间决策

**优化目标**

三个全局特征仍主要由亮度分开（luma-only 98.5%），
需要让“空间布局”进入决策。

**用户输入（提示词）**

```text
我的三类数据只用 f_luma 两级阈值就有 98.5% 准确率，
评委肯定会问“是不是纯亮度分类器”。
硬件已经有四象限 sumY（0x38/0x3C），但软件没用。
请设计一个不需要重出 bit 的空间决策规则，并给出如何标定阈值。
```

**LLM 回答（摘要）**

* `u=(max-min)/mean`；
* `u>=0.55` → mode1；`u<=0.30` → 信任 MLP；中间保持；
* 暗场均值 <5 时返回 0，避免噪声触发；
* 用“同亮度、不同空间布局”的 hard pair 标定阈值；
* 规则放 PS，不改 HDL/HLS。

**采用建议**

采用；用 4 场景 × 60 帧实测，确定 0.30/0.55；
hard pair 0：f_luma 9 vs 8，MLP 0/0，空间 0/1。

**验证**

`docs/results/hard_pairs.md`、`docs/results/live_scheduler.md`。

### 3.5 HDMI 分屏

**优化目标**

答辩时在 HDMI 上直接对比原始/处理后的同一区域。

**用户输入（提示词）**

```text
我想在 HDMI 上做左右分屏：左半原始、右半处理后的同一段源列，
1:1 不缩放，不要 scaler。输入 1280 宽，输出也是 1280。
请给出行缓冲和列选择的实现，以及验证方法。
```

**LLM 回答（摘要）**

* 加 640×24 bit 行缓冲；
* `col<640` 输出原始像素，同时把处理后像素写进行缓冲；
* `col>=640` 输出行缓冲；
* 列计数只在 `tvalid & tready` 的有效像素递增；
* 验证用“同帧自洽 + 错配项”两张表。

**采用建议**

采用；rev01 列计数在消隐期也自增，导致黑带/错位；
rev02 改成只在有效像素计数后通过。

**验证**

同帧自洽 RMS 0.09（<3），错配项 176（>100）。

### 4.3 `f_grad` 在真机上恒等于 2

**用户输入（提示词）**

```text
三个 MLP 特征里 f_grad 在板上一直是 2，std=0。
公式是 GRAD_SUM >> 20，是不是移位取太大了？
```

**LLM 回答（摘要）**

1280×720 平均梯度只有 0~5，`>>20` 会把典型值压成 0/1/2；
改成 `>>16`，典型值落到几十，仍在 int16 内。

**自我纠错**

第一次只改 Python 的 `MLP_FEAT_SHIFT`，忘了 HDL 的
`reg_f3_r <= acc_grad >> 16`；板上仍读旧值。
后来把“Python/HDL/HLS 三处移位必须一致”写成检查项。

**验证**

`check_features.py` 的“标签内不同取值”从 1 变成十几。

### 4.4 `stretch_param` 方向写反

**用户输入（提示词）**

```text
我按“对比度越低补偿越强”写了 stretch_param，
但板上实测 contrast=13 时 PARAM=128、26 时 140、75 时 244，
方向好像反了。逆光补偿到底该按什么方向？
```

**LLM 回答（摘要）**

逆光补偿是“暗部提亮 + 亮部压下”，即压低整体反差；
反差越大越需要强补偿。模型最初方向是错的。

**自我纠错**

纠正依据不是再问一次模型，而是板上 `std` 的实测方向：
逆光档 std 64.4→40.0（−38%），说明补偿在压对比。

**验证**

`docs/results/step5_compare.md`。

### 4.5 `PARAM` 写得进去、读回一直是 0

**用户输入（提示词）**

```text
regs.set_param(192) 后画面确实变亮，但 regs.param() 一直读 0。
写通道用 aw_addr[5:2]，读通道是 case(addr)，哪里错了？
```

**LLM 回答（摘要）**

写通道比较字索引，读通道比较字节地址；
新加的 0x34/0x38/0x3C 在读通道里写成 6'h0D/0E/0F，
永远命中 default。改成 6'h34/38/3C。

**自我纠错**

模型同时提醒 `reg_param` 只在复位分支赋值，上电值可能是 0；
而 PARAM=0 会让 mode0 增益 ×0（整屏黑），于是加上电初值 192。

**验证**

`12_verify_adaptive.ipynb` 的 `regs.param()/quads()` 读回正常。

**沉淀**

`skill/axil_register_contract`：寄存器表 → HDL 地址扫描。

### 4.6 权重更新了，板上还是旧模型

**用户输入（提示词）**

```text
我重训并导出了新的 mlp_weights.h，但板上 monitor 的判决和旧模型一样。
怎么确认 bitstream 里到底是哪份权重？
```

**LLM 回答（摘要）**

比较 `weights/mlp_weights.h`、`stage05_mlp_hls/src/mlp_weights.h`
和 `overlay/cv_ov5640.bit` 的时间/指纹；bit 比权重旧就说明没重出。

**自我纠错**

一开始只比权重和 HLS 源码，没比 bitstream；漏掉了“板上跑的是 bit”。

**验证**

`check_weight_sync.py` 报“bit 比权重旧 7972 分钟”；
重出后三者一致。

### 4.7 分屏 rev01 的黑带与左右错位

**用户输入（提示词）**

```text
分屏第一版每行都有黑带，左右内容还错位。
列计数 q_col 在行间消隐期也自增，是不是这个原因？
```

**LLM 回答（摘要）**

是。列计数必须只在 `tvalid & tready` 的有效像素递增，
行首清零；行缓冲写地址用同一个有效列计数。

**自我纠错**

模型一开始建议用行首/行尾判断，但实际流里 `tlast` 与消隐关系
要以仿真/抓帧为准；最后用有效像素计数最稳。

**验证**

`13_verify_split.ipynb`：RMS 0.09，列剖面中位差 1~2，错配 176。

### 4.8 数据采集“采废了”

**问题现象**

曝光从 256 扫到 736，luma 一直是 4.3；contrast 0.6、sharp 0.4，
三类都贴在噪声底。

**用户输入（提示词）**

```text
我扫曝光时 luma 一直 4.3 不动，contrast 0.6、sharp 0.4。
这是曝光寄存器没生效，还是画面根本没光？怎么快速区分？
```

**LLM 回答（摘要）**

先做“自动/手动曝光各读一次 luma”的光线自检：
两个都 ≈4 → 光没进来；有差别 → 光正常，是标定/摆法问题。
再检查灯电源、箱盖、镜头孔；曝光上限约 736 行，不够时要加增益。

**采用建议**

采集脚本加三道保护：光线自检、曝光×增益扫描、逐轮目标带检查。

**验证**

后续 540 帧数据 0 FAIL；暗光/逆光/常规中心回到 10/66/96。

### 4.9 置信度门限误杀/误放

**用户输入（提示词）**

```text
置信度门限用不归一化距离时，既放过 (34,8,40) 被判 0，
又误杀正常帧 (121,85,29)。怎么定门限才和 MLP 的训练空间一致？
```

**LLM 回答（摘要）**

MLP 在归一化空间里学边界，门限也应使用归一化距离；
规则改成“归一化距离 ≤12σ 且判决类必须是最近类（1.5 倍余量）”。

**采用建议**

采用；实测正常帧 0.2σ~10.5σ 不被误杀，
外推点 21σ/61σ 被拒。

**验证**

`auto_schedule.py` 日志出现“门限拒绝”，但模式不乱切。

## 10. 协作效果评估（对应报告 4.4）

### 10.1 效率

* 架构对比、寄存器表、HLS 接口、调试假设的初稿生成快；
* 但每次都要用板上实测确认，不能直接抄；
* 最大收益在“把失败现象转成可验证假设”，不是“一次写对代码”。

### 10.2 质量

* 增加了 `test_regs/test_hwh/test_spatial/offline_check` 等回归；
* 把“Python/HDL/HLS 三处移位一致”“权重/bit 同步”做成检查项；
* 数据体检 C1~C8 阻止了静止点数据进训练。

### 10.3 学习效果

* 理解了 AXIS 握手、AXI-Lite 地址译码、VDMA 通路、时序流水；
* 理解了 Q8.8 量化、归一化折叠、`w1` 饱和；
* 理解了“统计用硬件、决策用软件”的划分。

### 10.4 LLM 擅长的领域

| 擅长 | 不擅长/需人工 |
|---|---|
| 方案对比、接口/寄存器草案 | 不知道板子的真实时序/电气状态 |
| 把日志/现象转成假设 | 容易把“看起来合理”当成“实测正确” |
| 生成测试/文档/表格 | 容易漏掉 HDL/Python 两处同步 |
| 代码重构/命名/注释 | 不能替代板上测量和取舍 |

### 10.5 有效的 Prompt 技巧

1. **给现象，不给结论**：贴 WNS/日志/波形，不要先说“我觉得是 X”；
2. **一次只改一个变量**：让模型给 2~3 个假设，板上逐个排除；
3. **要求给验证方法**：每个建议必须说明“看到什么算过”；
4. **把实测回填**：模型说错时，贴板上数据，让它修正；
5. **要求沉淀**：每个 episode 最后问“这条经验能不能做成 Skill/判据”。
