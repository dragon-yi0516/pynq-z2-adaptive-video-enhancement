## 必须满足（缺一不可）

- `VERSION` 读回 **`0x00010407`**（`0x0001`=家族，`04`=修订，`07`=阶段）。
      `0x00010207` 是**时序违例、mode2 画面被采坏**的旧版，读到它说明板上还是旧 bitstream。
- 写 `MODE_SEL = 0` → 画面整体明显变亮（×1.5，高光会溢出，这是正常的）。
- 写 `MODE_SEL = 1` → 暗部变亮、亮部不再死白。
- 写 `MODE_SEL = 2` → 边缘变锐（噪点也会被强化，属正常）。
- **切换时画面不撕裂**：因为 `mode_active` 只在 tuser（帧边界）重采样。
- `MLP_OUTPUT` 仍然可用（阶段 6 的功能没被破坏）。
- `FRAME_CNT` 仍在约 27~30/秒 递增（720p30，**不是 60**；
      阶段 8 的 60 秒日志里实测 27.4 fps —— 说明加了处理逻辑没拖垮数据通路）。
- 构建日志里出现 `== 时序收敛：OK ==`（有 `WNS < 0` 就不算通过）。
      ✅ **2026-10-04 最终结果**（`timing_v3.rpt`）：
      **`All user specified timing constraints are met`** —— WNS **+0.134 ns**、
      TNS 0.000、失败端点 **0**（共 54580 个端点）。

      怎么走到这一步的（三段，都记在这里免得以后再踩）：
      1. 原始版本整份报告 WNS -4.044，3 个端点全在 `async_default` 组，位置是
         Xilinx AXI VDMA 内部异步 FIFO 的复位同步链（Recovery 检查，要求时间
         只有 0.034 ns = 两个异步时钟最坏对齐）→ 用 `tcl/timing_waiver.xdc`
         的 `set_false_path` 声明掉这两对时钟之间的路径；
      2. 加完约束后只剩 **-0.125 ns / 2 个端点**，而且在 Xilinx `v_demosaic`
         内部的 Debayer 插值路径上（16 级逻辑、数据路径 9.939ns）；
      3. 换实现策略重跑：place = `Explore`、route / phys_opt = `AggressiveExplore`
         → **+0.134 ns，全部收敛**。
- **`06_mode_manual.ipynb` 的「诊断」格**：三档的“输入亮度(IP 统计)”应当
      基本相同（LUMA_SUM/PIXEL_CNT 统计的是**处理前**的像素，模式不该改变它）。
      若某档的输入亮度本身就低，说明是摄像头 AEC 在动，而不是处理逻辑。

  修好之后这一格应该长这样（参考值来自出问题那次的实测）：

  | 模式 | 输入亮度 | 输出均值 | 水平差分 | 0 占比 | 满 255 占比 |
  |------|---------|---------|---------|--------|------------|
  | 0 | ≈112 | 最大（×1.5，亮部会顶到 255） | ~3 | 0% | 30~40% |
  | 1 | ≈112 | 中间 | ~3 | 0% | 0% |
  | 2 | ≈112 | **与 mode1 接近**（高通是均值保持的） | 明显更大（锐化） | **≈0%** | 少 |

  出问题那次的 mode2 是：输出均值 70.6、**0 占比 38.5%**、水平差分 62.8 ——
  三个数字都不对，说明像素值是在**采样时被采坏的**（时序），而不是算式算得不一样。

## 修订 03 / 04 改了什么（为什么）

时序报告（`cv_ov5640.runs/impl_1/cv_ov5640_wrapper_timing_summary_routed.rpt`）
是唯一的裁判，两轮修改都是照着它改的：

| 版本 | 最差路径 | WNS | 上板表现 |
|------|---------|-----|---------|
| 1.4 (修订 02) | `v_demosaic 输出寄存器 -> acc_luma2_reg`，14.663ns | **-5.093** | mode2 一片噪声：38.5% 像素被采成 0、水平差分 62.8 |
| 1.5 (修订 03) | `v_demosaic -> grad16_a_reg[7]` | -2.324（TNS 从 -453 降到 -17.4） | 已修复像素通路 |
| 1.6 (修订 04) | 自研逻辑域内已无违例；整份报告只剩 VDMA 异步 FIFO 的 3 个端点 | **`clk_fpga_0` +0.119，失败端点 0**；整份 -4.044（`async_default`） | 上板通过：mode0/1/2 三档实测与理论吻合（见上面那张表） |
| 1.6 + `timing_waiver.xdc` + Explore（**最终版，10-04**） | 全部收敛 | **+0.134，失败端点 0**（`All user specified timing constraints are met`） | 上板复验通过：阶段 8 / 阶段 9 都已在新 bit 上重跑 |

### 最终比特流是哪一块（重要）

因为这次只改了约束和实现策略、**没动 HDL**，板上 `VERSION` 仍是 `0x00010407`，
光看寄存器分不出新旧。所以用 md5 认：

| 版本 | md5 | 说明 |
|------|-----|------|
| 旧 bit（10-02 20:20） | `4F28A411A667627BB59A25DD19BF3905` | 时序 -4.044 那版，**不要再用了** |
| 最终 bit（10-04 20:33） | `C5A2DE701B2B99A51B7FC4DE44232A4E` | 约束 + Explore 之后，时序 met |

板上确认命令：

```bash
md5sum /home/xilinx/jupyter_notebooks/ai_video/overlay/cv_ov5640.bit
# 期望：c5a2de701b2b99a51b7fc4de44232a4e
```

配套文件（都在 `stage07_reconfig_array/`）：

- `timing_waiver.xdc`（实际放在工程的 `constrs_1` 里）—— 声明两个异步时钟域；
- `timing_v3.rpt` / `util_v3.rpt` —— 最终版时序与资源报告。

具体改动：

1. **像素通路两级流水**（修订 03）：当前像素/左邻像素先登记进本模块的寄存器，
   再从寄存器组合算到输出寄存器，最后输出寄存一级（tvalid/tuser/tlast 一起延迟）。
   这是修 mode2 画面的那一刀。
2. **mode 2 改写成无符号算式**（修订 03）：原来 `$signed(...)` 和 8 位无符号的 `c`
   混在一个表达式里，结果依赖"表达式宽度会不会被左值拓宽"这条细则，读起来有歧义。
   现在按 `c >= p` / `c < p` 分两支，全程无符号，语义只有一种读法。
3. **统计链路再切一级**（修订 04）：`亮度` 和 `梯度` 原来在同一级（三个乘加 + 求差
   全挤在一起），现在分开；并且亮度的源头从**输入端口**换成**本模块的 px1_*** 寄存器，
   把 v_demosaic 的输出 mux 和那段长走线从这条路径上摘掉。
   统计值因此比像素晚 4 拍，帧内累加的总和不变。

### 为什么必须看时序报告，不能只看"阶段完成"

这个工程从阶段 1 起每一版都在报 `failed to meet the timing`
（`grep -c "failed to meet the timing" ai_video/logs/*.log` 每份日志都是 1）。
也就是说"能出图"不等于"时序干净"——只是多数违例落在不影响画面的路径上。
所以 `tools/build_and_copy.tcl` 现在会在时序不收敛时把 WNS/TNS 和每条违例路径的
起点终点直接打到终端上。

另外：`rgb2dvi_0` 的 371MHz 串行域一直在报
`Generated clock ... has no logical paths from master clock`，从阶段 1 就有，
不影响 VDMA 抓帧，属于这块板子 DVI 输出的历史问题。

因为 HDL 改了，IP 版本同步涨到 **1.6**（`tcl/package_ip.tcl` 与
`tcl/insert_reconfig.tcl` 两处必须一致），否则工程里可能继续用旧的一份 IP。
- **可重复性**（`06_mode_manual.ipynb` 的「复验」格）：同一场景不动，
      按 `0,1,2,0,1,2` 各抓一帧，同一个模式两次读到的均值差异 ≤ 6 灰度。

  为什么必须加这一条：三种模式图是**先后三次**抓的，中间隔着不同时间。
  如果镜头前的东西动了、或者 OV5640 的自动曝光（AEC）还在收敛，均值变化里就
  混进了「场景自己变了」。这时「mode0 比 mode2 亮」这句话既可能是模式造成的，
  也可能是场景变亮造成的 —— 单看一次抓帧分不出来。
  同一模式两次读到同一个值，才能把「模式的作用」和「场景的漂移」分开。

  实测那一轮的均值是 `mode0 148.9 / mode1 107.0 / mode2 70.5`。
  mode0 是逐点 ×1.5（带饱和），所以它**最多**是 mode2 的 1.5 倍；
  148.9 / 70.5 ≈ 2.11 倍，超出了 ×1.5 能解释的范围，说明抓 mode0 那一帧时
  场景本身就比抓 mode2 时亮 —— 所以那次的数量对比不能当作干净证据，
  补齐上面的「复验」格才算数。

## 三种模式的实现与原因

| mode | 名称 | 运算 | 为什么这么做 |
|------|------|------|-------------|
| 0 | 暗光增强 | `c*3/2` 饱和 | 最省资源（一次乘 3、一次右移），效果直观 |
| 1 | 逆光补偿 | `c<96: c+c/2`；`c>160: c-(c-160)/4` | 只用移位和比较，天然就是“提暗压亮”的曲线 |
| 2 | 细节锐化 | `c + (c - 左邻)/2` | 一维高通，只要一个“左邻像素”寄存器，零 BRAM |

为什么不做二维卷积/拉普拉斯：那需要行缓存（BRAM）和跨行对齐，资源与调试成本高，
而本项目的重点在“MLP 判场景 + 阵列换模式”的闭环，一维锐化已能明显看出差别。

## 为什么特征提取要用处理前的像素

如果特征取自**处理后**的像素，会形成正反馈：

```
暗 → 切暗光增强 → 画面变亮 → 特征像“正常” → 又切回正常 → 画面变暗 → ...
```

结果是画面在两个模式之间抖。所以 `axis_video_proc` 里统计用的是输入像素，
处理只作用于输出像素。这一条在 `docs/02_why_this_design.md` 第 4 节也写了。
