### 这次的一个操作教训（已经修掉）

上一轮日志里出现过"两个实例同时写一个日志"：第 10 格点了两次，第二轮的收尾行
（`共切换 0 次`，因为它接手时 `MODE_SEL` 已等于当前类别）把第一轮的好结果盖在下面，
于是"最后一行"不合格。判别特征很好认：**心跳的 t 值会交替出现**（`t=50.1s` 与
`t=5.0s` 交错），而且日志里会出现第二次 `按 --base=…`。

第 10 格现在做了三件事，从根上避免：

1. 启动前 `pgrep -f auto_schedule.py`，有残留就先 `pkill` 并等它退出；
2. 启动时清空 `sched.log` / `sched_stdout.log`，保证**文件里只有本轮**，最后一行就是收尾行；
3. 不再固定 `sleep(10)`，而是**等收尾行出现**（最多 110 秒）再打印整份日志 ——
   免得看到空日志以为没跑起来、又点一次。

## 三个坑（都踩过）

1. **别写死 `python3`。** notebook 的 kernel 用的是
   `/usr/local/share/pynq-venv/bin/python3`（带 pynq），而 shell 里的 `python3`
   可能是系统解释器（没有 pynq）。用 `nohup python3 ... > /dev/null 2>&1 &` 启动时，
   如果解释器不对，脚本**秒退且什么都不打印**，看起来像"什么都没发生"。
   所以启动格改成 `sys.executable` + 把 stdout/stderr 写到 `sched_stdout.log`。
2. **别把 stderr 丢掉。** 出错信息是唯一线索，`> /dev/null` 会把它一起吞掉。
3. **别只等 2 秒就 tail。** 加载 overlay + 配 253 个摄像头寄存器要好几秒，
   启动格现在 `time.sleep(10)` 再 tail。

## 为什么还要 min-hold（时间闸）

真机上 MLP 会在相邻帧之间偶发抖动，`--debounce 3`（约 60ms）挡不住来回跳：
2026-10-02 那次日志里 **1.6 秒切了 4 次**（0→1→2→1→2）。
现在脚本多了一道 `--min-hold`（默认 1.5s）：两次切换之间至少隔这么久，
被挡下的次数会记在最后一行里（`因 min_hold(2.0s) 被挡下 N 次`）。
演示建议用 `--debounce 8 --min-hold 2.0`。

## 为什么从阶段 3 起 HDMI 一直是黑的（正常，但要给演示加回来）

采集和显示是**两条链**：

```
采集：OV5640 -> v_demosaic -> axis_video_proc -> VDMA0 S2MM -> DDR
显示：DDR -> VDMA0 MM2S -> VDMA1 S2MM -> DDR -> VDMA1 MM2S -> v_axi4s_vid_out -> rgb2dvi -> HDMI
```

阶段 0/1/2 用的是 `vp.start_hdmi_passthrough()`，四个通道都启动，所以屏幕有画面。
**阶段 3 起 notebook 只调 `vp.start_capture(vdma0, mode)`（只启动采集的 S2MM）**，
显示那半条链没人启动 → HDMI 没有数据 → 黑屏。这是当初为了让抓帧/统计不被打扰
有意简化的结果，**不是坏了**。

要恢复显示（同时保留自动调度），在启动调度脚本之前跑：

```python
vp.start_hdmi_passthrough(vdma0, vdma1, mode)
```

它会先 tie 再 start（顺序反了自动转发不生效）。屏幕出现画面后，
调度脚本用 `--base <地址>` 启动，**不碰 VDMA**，所以画面会一直留着，
而且能直接看到画质随场景自动切换 —— 这正是答辩要的效果。

## `Could not send I2C data` 是怎么回事

2026-10-03 的现象：notebook 已经配好摄像头（253 个寄存器），
后台脚本再 `bring_up()` 一遍时抛

```
RuntimeError: Could not send I2C data
```

（`lib/video_setup.py` 的 `init_camera` → `iic.send`）。根因是**两个进程抢同一路 I2C**：
notebook 的 kernel 持有 overlay 和 `axi_iic_0`，脚本再配一遍时从机不应答。
用户试过 `stop_all_channels` + `ol.free()` + `del` + `gc.collect()` —— 不解决，
因为问题不在 Python 对象，而在总线/控制器状态。

**正确做法：第二个进程不要去碰 I2C。** 传感器寄存器写一次就留在传感器里，
不会因为没有第二个 Python 进程而丢失。两种跑法：

1. 推荐：脚本用 `--base <axis_video_proc 的 AXI-Lite 基地址>`
   （notebook 里 `ol.ip_dict["axis_video_proc_0"]["phys_addr"]` 就能拿到）。
   键名是 **`phys_addr`**，写成 `phys_address` 会 `KeyError`（2026-10-03 卡过一轮）；
   本设计的实际值是 **0x43C20000**（见 `overlay/cv_ov5640.hwh` 里 axis_video_proc_0 的 `C_BASEADDR`），
   急用时可以直接 `--base 0x43C20000` 跳过 notebook 那一格。
   这种模式下脚本只 mmap 4KB 寄存器空间读写 `MODE_SEL` / `MLP_OUTPUT` / `FRAME_CNT`，
   **不加载 overlay、不碰 VDMA、不碰 I2C**，和 notebook 完全不抢资源。
2. 或者 `--no-camera`（仍然会加载 overlay 拿 IP 对象，但不重配摄像头）。
   脚本里也把这个失败做成了非致命：认失败就按"摄像头已经配好了"继续。

## `MLP_OUTPUT` 一直是同一个值（2026-10-03 白天读到 2、晚上读到 0）

先别改代码，先分清是哪一种。MLP 的三个输入是**硬件算出来的三个整数**，
`data/features.csv` 里三类的实测中心（每类 200 帧的均值）是：

| 类别 | 场景 | f_luma | f_luma2 | f_grad |
|------|------|--------|---------|--------|
| 0 | 暗光（镜头挡死 / 全黑） | 9.8 | 1.0 | 24.7 |
| 1 | 逆光（对着窗户，明暗对比大） | 67.4 | 39.1 | 29.6 |
| 2 | 常规 / 细节（正常室内 + 移动物体） | 109.3 | 54.7 | 34.6 |

也就是说这套 MLP **本质上是个亮度分级器**（三类主要靠 `f_luma` 分开：9.8 / 67 / 109）。
所以：

* 画面真的是黑的 → 判 0 是**对的**，改代码没用；
* 画面在变而 `MLP_OUTPUT` 不变 → 才是链路问题。

### 三步定位（`07_auto_schedule.ipynb` 里 `0) 体检` 那两格就是干这个的）

1. 跑 `0) 体检` 第一格，记下基线；
2. 改变场景（摘镜头盖 / 开灯 / 对着窗户 / 亮屏怼到镜头前）；
3. 跑第二格，按它的结论走：

| 现象 | 结论 | 处理 |
|------|------|------|
| `FRAME_CNT` 没涨 | 采集链停了 | 重跑第 2 格；还不行查摄像头 / VDMA |
| `FRAME_CNT` 在涨、特征不变 | 画面本身没变（全黑 / 镜头挡死） | 开灯、摘镜头盖、把亮的东西放进画面 |
| 特征在变、`MLP_START_CNT` 不涨 | 硬件启动握手问题 | 改 HDL 重出 bitstream（阶段 6 修订 02 修过一次） |
| 特征在变、`MLP_DONE_CNT` 不涨 | MLP 启动了没完成 | 查 `ap_clk` / `ap_rst`（`ap_rst` 高有效，必须反相） |
| 全都在变、`MLP_OUTPUT` 不变 | 场景真的落在同一个类里 | 见上面的类别表，把画面亮度拉开 |

### 演示时怎么造出「自动切换」

调度脚本只在「MLP 判出来的类别 ≠ 当前 MODE_SEL」时才切。所以：

* 先 `print(regs.mode_sel(), regs.mlp_output())`：两者**相等**就没得切；
* 想看到切换：先 `regs.set_mode(2)`（或把镜头对着亮处让 MLP=2），
  再把镜头转向暗处让 MLP 掉到 0 —— 会切一次 `2 -> 0`，画面亮度同时变，演示效果好。

### 日志里怎么事后确认

`auto_schedule.py --heartbeat 5` 每 5 秒写一条（起步时也有一条「起步状态」）：

```
[..] 心跳 t=5.0s MLP=0 模式=0：MODE_SEL=0 MLP_OUTPUT=0 FRAME_CNT=143 MLP_START=143 MLP_DONE=143 特征=(10, 1, 25)
```

特征一直是 `(10, 1, 25)` = 画面一直是黑的；特征在变而 `MLP` 不变，才需要往下查。
脚本自己还会在 `FRAME_CNT` 超过 2 秒不动时打警告、在特征超过 15 秒不变时打提示。

## 为什么要有 debounce

单帧的 MLP 判断会被自动曝光/噪声影响，偶尔闪一下。
如果一读到不同值就切，画面会疯狂闪。**连续 3 次同一个结论才切**，
这是本工程对方案书「VBlank 防抖」的具体落实：

```
确认（3 次一致）  ->  等帧边界  ->  写 MODE_SEL  ->  硬件下一帧生效
```

两道保险：软件防抖负责“不要频繁切”，硬件帧边界重采样负责“切的时候不撕裂”。

## 为什么用独立 .py 而不是 notebook 里 while True

见 `auto_schedule.py` 顶部注释。简单说：notebook 长循环会卡内核，答辩现场风险太大。

## 常见失败与处理

| 现象 | 原因 | 处理 |
|------|------|------|
| 日志里 `MLP` 一直在跳 | 场景本身模糊 / debounce 太小 | 加大 `--debounce`，或回阶段 3 重采更“干净”的三类 |
| 后台脚本启动就报 DMA 忙 | notebook 还占着 VDMA | 先跑「释放通道」那格，再启动脚本 |
| 后台脚本报 `RuntimeError: Could not send I2C data` | ①重新下载 bitstream 时相机被复位，SCCB 还没准备好；②notebook 内核还持着 axi_iic_0 | ①`lib/video_setup.py` 的 `init_camera` 已加 settle+4 次重试；②「释放通道」那格现在会 `ol.free()` + `del` + `gc.collect()`，实在不行就 Restart 内核 |
| 画面切换时闪一下黑 | 先写了 MODE_SEL 再等帧边界 | 脚本里顺序是 `wait_frame_boundary()` 然后 `set_mode()`，不要颠倒 |
| 日志没生成 | 权限/路径问题 | 用 `--log /home/xilinx/sched.log` 明确指定 |

### `Could not send I2C data` 的来龙去脉（2026-10-03 踩过）

现象：notebook 里跑得好好的，后台脚本一启动就在
`lib/video_setup.py` 的 `init_camera()` → `iic.send()` 抛异常，
而 `sched.log` 一行都没新增（因为 Logger 的第一条日志在 `bring_up` 之后）。

原因：**后台进程会自己再加载一遍 overlay**。PYNQ 判断"当前 overlay 是否已加载"
是按进程来的，所以新进程会把 bitstream 重新下载一次 → PL 重配 → 摄像头复位脚
（在这个设计里来自 PL）被拉了一下 → OV5640 要过一小会儿 SCCB 才应答，
而脚本立刻开始写 253 个寄存器 → 第一笔就 NAK。

处理：

1. `init_camera()` 现在会先 `sleep(0.2)`，并且整段配置最多重试 4 次
   （每次重试重建 AxiIIC 实例）——这是根治；
2. 「释放通道」那格顺手把 notebook 这边的 overlay 也放掉
   （`ol.free()` + `del` + `gc.collect()`），少一个进程抢同一个 IP；
3. 还不行就 Kernel → Restart 再跑后台脚本。
